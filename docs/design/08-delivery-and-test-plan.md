# 8) خطة التنفيذ والاختبار التدريجية

## 8.1 المبدأ
**"القرارات الغالية تتثبت بالتجربة الأول، قبل ما يتبني فوقها أي حاجة."**
كل مرحلة ليها **بوابة خروج** (Exit gate) بأرقام قابلة للقياس. مفيش انتقال للمرحلة
الجاية لو البوابة مقفولة — حتى لو "الشغل ماشي".

القرارات اللي لو غلطنا فيها هنندم (وعشان كده بتتختبر الأول):
1. SQLite يستحمل الحمل فعلًا؟ 2. نفس الكود يشتغل على PostgreSQL؟ 3. الدفتر بيحافظ على
الكميات وبيكشف التلاعب؟ 4. الجدول في المتصفح سريع مع بيانات حقيقية؟ 5. التثبيت
والتحديث والاستعادة بيشتغلوا على جهاز نضيف؟ 6. عقد الوحدات فعلًا بيعزلها؟

## 8.2 المراحل

### المرحلة 0 — تجارب إثبات (Spikes) — ~3 أسابيع
كود تجريبي **يترمي** بعدها؛ الهدف أرقام مش منتج.
| التجربة | النجاح = |
|---|---|
| S1: حمل الكتابة على SQLite (كاتب واحد) — 60 مستخدم افتراضي + 40 محطة مسح (Locust) لمدة ساعة | ≥ 50 أمر/ث، p99 < 150ms، صفر "locked"، WAL لا يتضخم |
| S2: نفس الاختبار على PostgreSQL بنفس الكود | نفس النتايج أو أحسن، بدون أي تعديل في منطق الأعمال |
| S3: دفتر 20 مليون سطر: تقرير يومي + تتبع للخلف | < 1ث للتقرير، < 5ث للاستدعاء |
| S4: قطع الكهرباء (kill -9 أثناء الكتابة، 1000 مرة) | القاعدة سليمة، سلسلة الـHash سليمة، مفيش أمر اتسجل نصه |
| S5: AG Grid بـ50 ألف صف + RTL عربي على جهاز مكتب عادي | تمرير سلس، فتح < 1ث |
| S6: مثبت Windows على جهاز نضيف بدون إنترنت → نسخ احتياطي → استعادة | < 15 دقيقة من الصفر لأول دخول |
| S7: وحدة تجريبية تتركب وتتشال (جداول + شاشة + hook) | النواة تشتغل بدونها، ومفيش import مباشر بين الوحدات |
| S8: طباعة ZPL مباشرة على طابعة Zebra/TSC حقيقية + ماسح USB/Bluetooth | ملصق مقروء، المسح بيوصل للحقل الصح |

**بوابة 0:** كل التجارب نجحت، أو القرار المعماري اتعدل رسميًا (ADR جديد) **قبل** المرحلة 1.

### المرحلة 1 — النواة الصلبة (Walking skeleton) — ~6 أسابيع
SYS (مستخدمين/صلاحيات/تدقيق/ترخيص) + Command bus + الدفتر + MDM (هيكل، أصناف، مسار
بسيط) + أمر عمل + Track-In/Out + شاشة محطة بدائية + شاشة استعلام واحدة بالقالب الكامل
+ نسخ احتياطي + مثبت.
**بوابة 1:** سيناريو "من الأمر للمنتج" يشتغل من أوله لآخره على جهاز نضيف، على القاعدتين،
وإعادة بناء الـprojections من الدفتر بتطلع نفس الأرقام.

### المرحلة 2 — اكتمال التنفيذ — ~6 أسابيع
فاقد/إعادة بأسباب، فرض المسار، Split/Merge، حركات عكسية بتوقيع، WIP، BOM بإصدارات،
ورديات ويوم إنتاج، TRC (لوتات واستهلاك وتتبع)، LBL، استيراد Excel.
**بوابة 2:** اختبار حفظ الكمية العشوائي (§8.3) بيعدي 10,000 سيناريو؛ تتبع 20 مليون سطر < 5ث.

### المرحلة 3 — الجودة والكفاءة والرؤية — ~6 أسابيع
QMS أساسي (فحص، عيوب، حجز/إفراج)، OEE يدوي، لوحات الخط والمصنع، التقارير، نظام
التصميم النهائي (بعد صور G-MES4)، الترجمة الكاملة.
**بوابة 3:** 5 مستخدمين حقيقيين (عامل، مشرف، جودة، مخطط، مدير) يخلصوا مهامهم بدون
مساعدة في اختبار قابلية استخدام؛ لوحة الخط بتتحدث < 2ث.

### المرحلة 4 — التجهيز للبيع (Hardening) — ~4 أسابيع
تحديث offline بالرجوع التلقائي، اختبار ترقية من كل إصدار، أمان (ASVS L2 مراجعة)،
Support bundle، التوثيق (دليل مستخدم عربي + فيديوهات قصيرة)، أداء نهائي.
**بوابة 4:** Release Candidate يعدي كل الاختبارات + تمرين كارثة كامل (الجهاز اتحرق → جهاز جديد → استعادة) < ساعة.

### المرحلة 5 — مصنع تجريبي (Pilot) — ~8 أسابيع
خط واحد → المصنع كله. **في الأسبوعين الأولين، تشغيل موازي** (Shadow) مع الطريقة
الحالية (ورق/Excel) ومقارنة الأرقام يوميًا. أي فرق = bug لحد ما يثبت العكس.
**بوابة 5:** أسبوعين متتاليين الأرقام متطابقة، صفر فقد بيانات، والمصنع مش عايز يرجع للورق.
بعدها بس: V1.0 للبيع.

**الإجمالي التقريبي لـV1.0:** ~8–9 شهور لفريق صغير (2–3 مطورين + مصمم جزئي + خبير
تصنيع استشاري). التقدير ده يتراجع بعد المرحلة 0.

### بعد V1.0
V1.1 (Linux/Docker) → V1.5 (TOOL، ALM، LBR، NCR، DOC، جدولة التقارير) → V2 (EDGE، CMMS،
SPC، APS، ERP connectors) → V3 (Multi-site، HA، تحليلات).

## 8.3 استراتيجية الاختبار (هرم الاختبار)

| المستوى | إيه | أداة | متى |
|---|---|---|---|
| **Unit** | منطق نقي: الحالات، الحسابات، OEE حسب ISO 22400، الوردية/يوم الإنتاج | pytest | كل commit |
| **Domain scenarios** | "Given حالة، When أمر، Then حركات في الدفتر + حالة" لكل أمر ولكل انتقال ممنوع | pytest + fixtures | كل commit |
| **Property-based** | آلاف السيناريوهات العشوائية (مسح، فاقد، تقسيم، عكس…) و**قاعدة حفظ الكمية لازم تفضل صح** | Hypothesis | كل commit |
| **Projection rebuild** | امسح جداول الحالة، أعد البناء من الدفتر، قارن | pytest | كل commit |
| **Ledger integrity** | تعديل سطر يدويًا → `verify-ledger` لازم يكشفه ويحدد مكانه | pytest | كل commit |
| **Dual-DB** | **كل** ما فوق على SQLite **و** PostgreSQL | CI matrix | كل commit |
| **Contract tests** | عقد كل وحدة: جداولها بس، مفيش imports ممنوعة، الـhooks بترجع موافقة/رفض بس | import-linter + pytest | كل commit |
| **API** | كل endpoint: الصلاحيات (مسموح/ممنوع لكل دور)، التحقق، الـidempotency (نفس command_id مرتين = مرة) | pytest + httpx | كل commit |
| **E2E UI** | التدفقات 1–7 في المتصفح، عربي وإنجليزي | Playwright | كل PR |
| **Migration** | ترقية من كل إصدار سابق مدعوم على بيانات حقيقية مجهولة الهوية | CI | كل إصدار |
| **Load** | S1/S2 بشكل مستمر؛ تراجع > 20% يفشّل الإصدار | Locust | ليلي |
| **Chaos** | kill -9 أثناء الكتابة، امتلاء القرص، ساعة الجهاز غلط، قطع الشبكة عن المحطة | سكربتات | ليلي |
| **Backup/restore** | نسخ → استعادة → تحقق → مقارنة أعداد وHash | CI | ليلي |
| **Licenses/security** | رفض GPL/AGPL، pip-audit، npm audit، فحص أسرار | CI | كل commit |
| **Mutation** | نكسر الكود عمدًا ونتأكد إن اختبار بيفشل (درس مشروع الأتمتة: "اختبار أخضر ميثبتش حاجة لحد ما يتخلى يفشل") | mutmut على النواة | أسبوعي |
| **Installer** | تثبيت صامت على VM ويندوز نضيفة بدون إنترنت | CI (Windows runner) | كل إصدار |

**تغطية الأوامر:** كل أمر في النواة له على الأقل: سيناريو ناجح، سيناريو رفض لكل قاعدة،
سيناريو تكرار، وسيناريو تزامن (اتنين في نفس اللحظة).

## 8.4 قواعد العمل اللي بتحمينا من الندم (Guardrails)

1. **ADR لكل قرار كبير** (تقنية، مكتبة، شكل جدول أساسي، تغيير عقد). القرار بيتكتب
   بسببه والبدائل المرفوضة. تغيير قرار = ADR جديد يلغي القديم، مش تعديل صامت.
2. **سجل تاريخ (HISTORY.md)** بنفس شكل مشروع الأتمتة: Symptom / Cause / Fix / Lesson
   لكل bug أو اكتشاف — من أول يوم.
3. **العقود قبل الكود:** OpenAPI + جداول الوحدة + الأحداث بتتراجع قبل التنفيذ.
4. **Feature flags** لأي حاجة نص-جاهزة بدل فروع طويلة.
5. **Semantic versioning للنواة**؛ الـAPI العام وأحداث الـoutbox مبيتكسروش في إصدار فرعي.
6. **ممنوع**: SQL خاص بقاعدة واحدة في منطق الأعمال، float في الكميات، `datetime.now()`
   من غير المصدر الموحد، `sleep` ثابت في الاختبارات، استيراد بين الوحدات. كل ده بيتفحص آليًا.
7. **بيانات حقيقية مجهولة الهوية** من المصنع التجريبي تبقى مجموعة اختبار دائمة.
8. **"Definition of Done"** لأي ميزة: كود + اختبارات على القاعدتين + ترجمة عربي/إنجليزي
   + صلاحيات + تدقيق + توثيق المستخدم + سطر في HISTORY لو في اكتشاف.

## 8.5 مخاطر رئيسية وخطة التعامل

| الخطر | الاحتمال | الأثر | التعامل |
|---|---|---|---|
| SQLite مايستحملش حمل مصنع معين | منخفض | متوسط | PostgreSQL مدعوم من يوم 1 + أداة تحويل مختبرة |
| العمال مش بيسجلوا (المشكلة البشرية رقم 1 في MES) | **عالي** | **عالي** | شاشة محطة بمسح واحد، مفيش كتابة، اختبار مع عمال حقيقيين في المرحلة 3، وV2 عدادات تلقائية |
| تخصيصات كل عميل تفرّق الكود | عالي | عالي | حقول مخصصة + إعدادات + قوالب فقط؛ مفيش فروع كود لعميل |
| نطاق بيكبر قبل الإطلاق | عالي | عالي | §7.4 + بوابات المراحل |
| ماكينات متنوعة جدًا في V2 | عالي | متوسط | الـEdge منفصل + إدخال I/O بسيط كحل عام رخيص |
| الاعتماد على شخص واحد يعرف النظام | متوسط | عالي | ADRs + HISTORY + اختبارات كتوثيق حي |
| مشاكل ترخيص مكتبات | منخفض | عالي | فحص آلي + مراجعة قانونية لمكتبات الـEdge |
