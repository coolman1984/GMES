# E4) خريطة المعرفات بين الأنظمة

## E4.1 المشكلة
كل نظام له أسلوب مختلف في المفاتيح اليوم، ولا يجوز تغيير مفاتيح نظام قائم:

| النظام | أسلوب المفتاح | مثال |
|---|---|---|
| ميزان | `INTEGER` تلقائي + كود فريد (`sku`، `code`) | item `id=42`, `sku='RM-STEEL'` |
| الثري دي | نص يولده العميل، فريد **داخل المشروع** | project `p_…`, item `it_…` |
| BAMS | معرفات عشوائية نصية | — |
| التصنيع (GMES) | UUIDv7 (ADR-007) | — |
| نظام ERP خارجي | Material Number، Plant، Storage Location | `MAT-1001`, `PL01` |

## E4.2 الحل: هوية عالمية + أصل محلي + كود بشري

كل كيان على السلك يحمل ثلاثة أشياء:
1. **`id` عالمي (UUID)** — يصنعه **المالك** مرة واحدة ولا يتغير أبدًا.
2. **`origin`** = `{app, type, key}` — المفتاح المحلي عند المالك (للدعم الفني والتتبع).
3. **`code`** — الكود البشري (SKU، كود المخزن…) للبحث والمطابقة وقت التبنّي.

### كيف يصنع مالك بمفاتيح رقمية (ميزان) هوية عالمية بدون تعديل قاعدته؟
**UUIDv5 حتمي**: `id = uuidv5(namespace = company_id, name = "mizan:item:42")`.
- نفس المدخل → نفس الـUUID دائمًا، حتى لو ضاعت حالة الموصل وأُعيد بناؤها.
- لا جدول ربط يمكن أن يتلف، ولا تعديل في ميزان.
- عندما يُبنى لاحقًا موديول eco أصلي داخل ميزان، يستخدم **نفس المعادلة** فلا تتغير أي هوية.

### معرف الشركة (الجذر)
`company_id` = UUIDv7 يُولد **مرة واحدة** عند أول تطبيق يُثبت في الشركة، ويُنسخ لباقي التطبيقات عند
الاقتران (Pairing). هو الـnamespace لكل UUIDv5، فمستحيل تتصادم هويات شركتين.

## E4.3 الخريطة لكل كيان

| الكيان | الهوية العالمية | عند المالك | عند المستهلكين | مفتاح المطابقة وقت التبنّي |
|---|---|---|---|---|
| الشركة | `company_id` (v7) | إعداد في كل تطبيق | إعداد | — |
| الصنف | v5(`mizan:item:<id>`) أو v7 لو التصنيع هو المالك البديل | ميزان `items.id` | التصنيع `mdm_item.id` = نفس الـUUID + `origin` | `sku` |
| وحدة القياس | كود نصي (`PCS`, `KG`) داخل الصنف | ميزان `item_units` | التصنيع | الكود |
| المخزن | v5(`mizan:warehouse:<id>`) | ميزان `warehouses.id` | التصنيع `mdm_warehouse` | `code` |
| الخط/المحطة/المعدة | v7 من التصنيع | التصنيع | الثري دي: `item.meta["eco.ref"] = "eco:station:<uuid>"`؛ ميزان: (مستقبلًا) مركز تكلفة | كود المحطة |
| عنصر مرسوم | `(layout_id, item_id)` من الثري دي | الثري دي | التصنيع يحفظ `spatial_ref` | — |
| أمر الإنتاج | v7 من التصنيع | التصنيع | ميزان: `stock_docs.reference = "eco:<event-id>"` + المذكرة تحمل كود الأمر | كود الأمر |
| الحدث | v7 من المنتج (`id` في الظرف) | Feed المنتج | Inbox المستهلك `(source,id)`؛ ميزان: `reference` | — |
| الموظف | **UUIDv5(company, `hr:employee:<Employee_ID>`)** — نفس القيمة في Python (`uuid.uuid5`) وTypeScript (`hrId`)، مختبرة | HR-System (`E000001`) | التصنيع `mdm_employee.id` + `performed_by.person`؛ ميزان/الثري دي لاحقًا | رقم الموظف |
| يوم الحضور | UUIDv5(company, `hr:attendance:<Attendance_ID>`) | HR-System | التصنيع `mdm_attendance_day` | Attendance_ID |
| مركز العمل/المحطة عند HR | كود نصي (`Work_Center_ID`, `Line_ID`) | HR-System (للجدولة فقط) | يُطابق بكود المحطة في التصنيع (مالك هوية المحطة) | الكود |
| المستخدم | **غير عالمي** — لكل تطبيق حساباته | — | يُرسل كنص للعرض فقط `performed_by.user` | — |
| اللوت | (item_id, lot_no) طبيعي | ميزان للموردة / التصنيع للمنتجة | الطرف الآخر ينشئ نفس `lot_no` | lot_no |
| خطة إنتاج خارجية (استيراد مستقبلي) | — | النظام الخارجي | `origin = {app:'external-plan', type:'plan', key:'…'}` | كود الأمر في النظام الخارجي |

## E4.4 قواعد
- **ممنوع** استخدام المفتاح المحلي لنظام آخر كمفتاح عندي (مثلًا تخزين `mizan item 42` كمفتاح أجنبي). أحفظ الـUUID + `origin` للعرض فقط.
- **ممنوع** إعادة استخدام هوية لكيان آخر ولو اتلغى الأول.
- تغيير كود بشري (SKU) لا يغير الهوية؛ المستهلك يحدّث المرآة.
